# 外送快閃 實作規劃書

系統設計（架構、演算法、API 格式、指標定義、部署參數）以 [README.md](../README.md) 為準。本文件只規定**實作順序、規則與完成條件**。

## 使用方式

- 依階段 P0 到 P8 實作。每個階段的完成條件全部打勾，才算完成。
- 接手時，告訴 agent：「讀 README.md 與 docs/規劃書.md，從第一個未打勾的項目開始」，或直接指定階段，例如「從 P4 開始」。
- 完成一項就把 `- [ ]` 改為 `- [x]`，與程式碼一起 commit。
- 實作時若需偏離 README 的設計，先修改 README 再寫程式。

階段依賴（箭頭左側完成後才能開始右側）：

```
P0 → P1 → P2 → P3 ─┐
     P1 → P4 → P5 ─┼→ P7 → P8
P0 → P6 ───────────┘
```

P2/P3、P4/P5、P6 可由不同人平行進行，彼此只依賴 README 第 5 節的 API 格式。

## 共通規則

1. **語言與套件**：Python 3.12、FastAPI、uvicorn、httpx、pytest。不加入其他相依套件，除非先更新本文件。
2. **不使用資料庫**，也不使用 Redis、Firestore 等外部狀態。
3. **不做阻擋**：任何服務都不得實作速率限制、IP 限制、驗證或防濫用機制。
4. **CPU 密集的 endpoint 一律用 `def`**，不可用 `async def`，避免阻塞 event loop。
5. **演算法與框架分離**：`shared/` 與 `dispatch/` 的演算法模組不得 import FastAPI，可直接單元測試。
6. **可調參數一律走環境變數**，預設值與 README 第 8 節一致，集中在各服務的 `config.py` 讀取。
7. **時間可注入**：hub 的指標模組與 loadtest 的排程器，透過參數接收時鐘函式，測試時以假時鐘驅動。
8. **hub 只能單一 process**：uvicorn 不可開多個 worker，因為指標只存在記憶體。
9. **前端不依賴外部資源**：純 HTML、CSS、JS，不使用 CDN 或建置工具，圖表和地圖都用 SVG 自行繪製。
10. **測試先行**：每個模組先寫 pytest，再寫實作；`pytest` 全數通過才能勾選完成條件。

## P1 城市路網 `shared/citymap.py`

依 README 4.1 實作，所有輸出只由 `CITY_GRID_SIZE` 和固定的 `CITY_SEED` 決定。

做法要點：

- 路口以 `(x, y)` 表示，邊以無向的路口對表示。
- 封閉路段：逐條隨機挑選並嘗試移除，以 BFS 確認仍然連通才真正移除，直到達到約 10%。
- 主幹道：選定數條完整的橫線與直線，基礎通行時間 15 秒，一般道路 30 秒。
- 店家放在不同的路口，菜單寫死在程式中，每項包含 `id`、`name`、`price`、`prep_min`。
- `address_to_node(address)`：對地址做 SHA-256，取模數對應到路口。
- `to_map_json()`：輸出 `/api/map` 的內容，包含尺寸、封閉路段、主幹道、店家與菜單。

完成條件：

- [x] 相同參數產生兩次，結果完全相同
- [x] 路網連通（測試中用 BFS 驗證）
- [x] 封閉比例在 8% 到 12% 之間
- [x] 相同地址永遠對應到同一個路口
- [x] `to_map_json()` 的輸出可以序列化成 JSON，且在 `CITY_GRID_SIZE=60` 時小於 200 KB

## P2 派單核心 `dispatch/engine.py`

依 README 4.2 實作。對外只暴露 `dispatch_order(order, now, rng) -> result`，其中 `now` 與 `rng` 由呼叫端注入。

做法要點：

- Dijkstra 用 `heapq` 自行實作，提供兩種模式：完整搜尋（從單一起點到所有點）和點對點搜尋（目標出列即停止）。
- 路況係數：`f(edge, minute)` 是決定性函式，回傳 1.0 到 2.0；每筆訂單計算一次權重表。
- 替代路線（懲罰法）：在權重表的副本上，把已找到路線的邊乘以 `ALT_PENALTY` 後重新搜尋；回報的 ETA 用原始權重計算。
- 店家到顧客的替代路線只算一次，所有候選人共用。
- 行程計算：`pickup_s = max(arrive_restaurant_s, 最長備餐秒數)`，`deliver_s = pickup_s + 送餐路線秒數`。

完成條件：

- [x] 在 5×5 小圖上，Dijkstra 的結果與暴力窮舉一致
- [x] 替代路線的數量正確，且彼此不完全相同
- [x] 選中的候選人分數不高於其他候選人
- [x] `arrive_restaurant_s ≤ pickup_s < deliver_s`
- [x] 相同的 `rng` 種子與 `now`，產生相同結果
- [x] 量測腳本 `python -m dispatch.bench` 輸出 100 筆帶種子訂單的平均 `compute_ms`；在本機上調整預設參數，使結果落在 50 到 100 ms（Cloud Run 通常比本機慢，最後以 P8 校準為準）

## P3 派單 API `dispatch/main.py`

依 README 5.1 實作。

做法要點：

- 啟動時取得 `instance_id`：以 `GET http://metadata.google.internal/computeMetadata/v1/instance/id` 搭配標頭 `Metadata-Flavor: Google` 取得；失敗時改用 `local-{hostname}-{pid}`。
- `service` 取自環境變數 `K_SERVICE`，未設定時用 `local`。
- 有帶 `seed` 時用 `random.Random(seed)`，否則用 `random.Random(order_id)`，讓同一筆訂單在兩個版本得到相同結果；顧客位置依照「有地址→雜湊，無地址→`rng` 隨機」決定。
- CORS 只允許 `ALLOWED_ORIGIN`。
- `Dockerfile`（repo 根目錄）：依 `APP` 啟動 `dispatch.main:app` 或 `hub.main:app`，監聽 `$PORT`，單一 worker。

- [x] 帶相同 `seed` 的兩次請求，除了 `compute_ms` 以外的回應完全相同

## P4 hub 後端 `hub/`

依 README 5.2 與第 6 節實作。

做法要點：

- `hub/metrics.py`：以「目標（fixed/auto）× 來源（student/loadtest）」為維度，用 600 格的環狀陣列保存每秒資料。每格記錄各 outcome 的計數、延遲樣本（上限 200 筆）與 instance ID。資料以 hub 收到的時間分格，不使用回報方的時間戳，避免兩邊時鐘不一致。

- SSE：一個背景工作每秒計算一次快照，廣播給所有連線；客戶端斷線時清除對應的佇列。
- `/api/config` 從環境變數 `FIXED_URL`、`AUTO_URL`、`TIMEOUT_MS` 讀取。
- `/` 與 `/static` 提供 `hub/static/` 的內容。

完成條件：

- [x] 假時鐘測試：超過 60 秒的資料不計入滾動指標
- [x] 假時鐘測試：instance ID 10 秒未出現就不計入活躍數
- [x] 分位數計算正確（以已知的樣本驗證 p50、p95）

## P5 前端 `hub/static/`

依 README 第 2 節與第 6 節實作，畫面以手機寬度 375px 為準。

做法要點：

- 載入時取得 `/api/config` 與 `/api/map`。
- 點餐：店家卡片 → 菜單數量 → 選填資料（預設收合）→ 送出。
- 送出時產生 `order_id`（`crypto.randomUUID()`），用 `fetch` 平行呼叫兩個服務，各自搭配 `AbortController`，在 `timeout_ms` 時中斷。
- 兩張狀態卡：等待中顯示每 0.1 秒更新一次的「已等待 N 秒」；完成後顯示結果或失敗原因。
- 地圖：SVG 畫出路網、店家、顧客與路線，可以切換固定版和擴展版的結果，預設顯示先成功的那一邊。外送員依 `schedule` 移動，整趟壓縮成 30 秒。
- 兩邊都結束後，送出 `/api/reports/order`，然後才允許再次下單。
- Debug 按鈕：展開時建立 `EventSource`，收起時關閉；寬度 ≥ 768px 時兩欄並排。

## P6 壓力測試工具 `loadtest/`

依 README 第 7 節實作。

做法要點：

- 排程器：依照「目前時間對應的速率」計算下一筆的發送時刻（加壓期間線性增加），每到時刻就建立一個 task，不等待前一筆回應。
- 每個目標用一個 `httpx.AsyncClient`，`limits` 上限設為 2000 個連線；同時進行中的請求超過上限時，記為 `dropped`。
- 訂單內容：從 `/api/map`（向 hub 取得）隨機挑選店家與品項，隨機產生地址或留空。
- 每秒彙總：把該秒內完成的請求依 outcome 計數，延遲樣本超過 200 筆時隨機抽樣，連同 instance ID 回報 hub；回報失敗只顯示警告，壓測照常繼續。
- 終端機每秒印一行：各目標的送出數、成功數、失敗數、`dropped` 數、p95。
- `probe`：從 1 rps 開始，每 15 秒增加 1 rps，使用固定 `seed`；當 15 秒內的失敗率超過 5% 時停止，輸出前一階段的速率作為容量 C。

完成條件：

- [ ] 假時鐘測試：`--rate 10 --ramp 0` 跑 10 秒，排程出 100 筆（±1）
- [ ] 假時鐘測試：加壓期間的瞬時速率線性增加
- [ ] 彙總測試：抽樣後不超過 200 筆，各 outcome 計數正確
- [ ] 對本機的 dispatch 跑 30 秒，hub 儀表板可以看到壓測數據
- [ ] Ctrl+C 時送出最後一筆回報後結束，不留下錯誤訊息

## 免費額度控制

- 平時三個服務的 min-instances 都設為 0，展示前才執行 `warm`，結束後執行 `cool`。
- `dispatch-auto` 的 max-instances 上限為 10，壓測一律指定 `--duration`。
- 只保留最新的映像檔，Artifact Registry 中的舊版要刪除。
- 部署前，到 GCP 定價頁確認 Cloud Run、Cloud Build、Artifact Registry 的免費額度與出站流量計費方式。

## 報告對照要點

- **選題理由**：外送平台的流量集中在用餐尖峰，而且每筆訂單都需要即時派單運算。
- **Auto Scaling 的特性**：依負載自動增減 instance，不需要為尖峰預先配置容量，離峰時可以縮到最少。
- **有無擴展的差別**：兩個版本使用同一份映像檔、相同規格，唯一的差別是能否擴展；觀眾在同一筆訂單上同時看到兩種結果。
