# 擴展過程趨勢圖與上限 10 台 設計文件

- 日期：2026-10-12
- 範圍：Debug 儀表板多一張「機器數」趨勢圖；`dispatch-auto` 的上限由 8 台改成 10 台
- 依附：README（權威說明）、`docs/規劃書.md` P9

## 1. 目的與成功標準

**目的**：讓觀眾在 Debug 儀表板上直接看到 Auto Scaling 的**過程**，不必切到 GCP 主控台：壓測開始後，擴展版的機器數一台一台往上長；壓測結束、配送送達後再往下降。固定版則一直停在 1 台。

**現況的缺口**：儀表板只有「個體數」一個數字（最近 10 秒），趨勢圖只畫成功率與平均回應時間，看不到機器數隨時間的變化。

**成功標準**
1. 趨勢圖最上面多一張「機器數」，跟成功率、平均回應時間對齊同一條時間軸（最近 10 分鐘，每 10 秒一點）。
2. 圖上有一條「擴展版上限 10 台」的虛線；本機模式（擴展版是 8 個 worker）時虛線在 8。
3. 固定版過載、請求全部失敗時，線是斷開的，滑鼠移過去顯示「全部失敗，拿不到機器編號」，而不是掉到 0 台。
4. 壓測期間，擴展版的線往上爬、壓測結束後往下降，趨勢跟 GCP 主控台的執行個體數一致。
5. `dispatch-auto` 的上限是 10 台；README 和規劃書不再寫 8 台（本機模式的 8 個 worker 除外）。

## 2. 指標：趨勢圖每一點的 `instances`

`web/metrics.py` 的趨勢圖每一點，在每個目標底下多一個欄位 `instances`，規則跟卡片上的「個體數」相同，只是視窗改成那一點的 10 秒：

| 那 10 秒的情況 | `instances` |
|---|---|
| 沒有任何完成的請求 | `0` |
| 有完成的請求，且至少有一筆帶回 `instance_id` | 不同 `instance_id` 的數量 |
| 有完成的請求，但一個 `instance_id` 都沒有（全部逾時、忙碌或錯誤） | `null` |

- 「完成的請求」＝ `ok`、`timeout`、`busy`、`error` 的總和，觀眾與壓力測試合計，下單與追蹤都算。
- 只有成功的回應帶得回 `instance_id`，這是全部失敗時改用 `null` 的原因：畫成 0 會讓人以為機器不見了。
- 已結束的區間照原本的方式快取，寫入規則不變。

趨勢圖每一點的格式變成：

```json
{ "t": 1759999410,
  "fixed": { "success_rate": 0.13, "avg_ms": 9400, "instances": 1 },
  "auto":  { "success_rate": 1.0,  "avg_ms": 380,  "instances": 7 } }
```

卡片上的 `targets.*.instances` 不變。

## 3. 上限設定

| 項目 | 值 |
|---|---|
| `dispatch-auto` 的 `--max-instances` | 10（原本 8） |
| web 的新環境變數 `AUTO_MAX_INSTANCES` | 預設 10，寫在 `web/config.py` |
| `/api/config` 新欄位 | `auto_max_instances`（整數） |
| 本機模式 | `run_local.bat`、`run_local_formac.sh` 啟動 web 前設 `AUTO_MAX_INSTANCES=8`，跟擴展版的 8 個 worker 一致 |

預設值用 10，是為了雲端部署時就算忘了設環境變數，虛線也對；本機腳本則明確設成 8。

## 4. 前端：「機器數」圖

- **位置**：`#dash-charts` 裡的第一張圖，`data-metric="instances"`，標題「機器數」，滑鼠停在標題上說明「每 10 秒內有處理請求的機器數；只有成功的回應帶得回機器編號」。
- **畫法**：階梯線，台數一格一格變化，不畫斜線。兩條線（固定版、擴展版）用現有的顏色。前後都沒有資料的單一點，照現有圖的規則畫成一個點。
- **Y 軸**：最大值 ＝ 上限與資料最大值兩者取大，刻度為 0、一半（無條件進位）、最大值，只標整數，例如上限 10 時為 0、5、10。
- **上限虛線**：在 Y＝`auto_max_instances` 畫一條擴展版顏色的虛線，右上方標「上限 10 台」。固定版的上限 1 台不另畫。
- **圖例**：兩邊各顯示最新一個有值的點，格式「7 台」；沒有資料時「—」。
- **提示框**：時間區間，加上兩邊的台數。某一邊為 `null` 且該點成功率為 0 時，那一邊顯示「全部失敗，拿不到機器編號」。
- **上限從哪來**：`app.js` 載入 `/api/config` 後，把 `auto_max_instances` 交給儀表板。設定還沒載入前先用 10，載入後重畫。
- 手機版的趨勢圖區塊預設收起的規則不變。

`web/static/logic.js` 新增兩個純函式，方便測試：
- `stepPath(values, x, y)`：階梯線的 SVG path，遇到 `null` 斷開，規則與 `chartPath` 相同。
- `countAxisMax(values, cap)`：Y 軸最大值（上限與資料最大值取大，至少為 1）。

## 6. 測試

- `tests/test_metrics.py`
  - 沒有請求的區間 `instances` 為 0。
  - 有成功請求時，`instances` 為該 10 秒內不同 `instance_id` 的數量；觀眾回報與壓測回報的 `instance_ids` 合併計算。
  - 有請求但全部失敗時，`instances` 為 `null`。
  - 原本「每一點只有 `success_rate`、`avg_ms`」的檢查改成三個欄位。
- `tests/test_web_api.py`：`/api/config` 回傳 `auto_max_instances`；預設 10、可用環境變數覆蓋。
- `tests/js/logic.test.mjs`：`stepPath` 的階梯與 `null` 斷開；`countAxisMax` 取大與最小值 1。
- 本機實際操作：`run_local.bat` 加上本機壓測，展開趨勢圖，確認機器數圖有畫出來、虛線在 8、壓測結束後線往下降，並截圖。

## 7. 部署與驗收（使用者自己操作）

dispatch 的程式沒有改，不需要換映像檔，只改上限；web 要換成新映像檔，並設定上限：

1. 建新映像檔（`v3`）。
2. `gcloud.cmd run services update web --region asia-east1 --image <v3 映像檔> --update-env-vars AUTO_MAX_INSTANCES=10`
3. `gcloud.cmd run services update dispatch-auto --region asia-east1 --max-instances=10`
4. 驗收：用展示速率跑一次壓測，確認擴展版長到 10 台附近、成功率維持在 95% 以上，圖上的虛線在 10。若碰到 10 台、成功率又往下掉，就把壓測速率調低。
5. 費用：10 台跑 10 分鐘約 6,000 vCPU 秒，Cloud Run 免費額度每月 18 萬 vCPU 秒。

## 8. 不做的事

- 機器格子、每台機器的負載顏色（要改壓測工具回報 web 的格式）。
- 每秒更新的即時圖、投影用的大畫面。
- 用 `probe` 校準後再決定上限（上限直接定為 10 台）。
